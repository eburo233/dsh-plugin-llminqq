# 记忆系统

> 每个对端（群 / 私聊）一份见闻录。这是我自己维护的，不是桥自动写的。
> 想不起某件事的时候翻这里。只记有用的：谁常说什么、最近在聊什么、答应过谁什么、什么话题别再提。

## v4：按人归集、按通道可见（owner / visibility / is_self）

v3 的记忆完全按**会话**（`peer`）分开：

```
c2c-3022464706      ← 他私聊说的
group-1017567471    ← 群里的所有发言（不分谁说的）
```

后果很实在：**同一个人在私聊说过的事，群里聊天时我想不起来。** 检索只能看到
「本通道里说过的话」，跨不了通道。群聊那半边还是「大锅饭」——315 条记忆分不清
哪句是信风说的、哪句是别人说的。

v4 把索引从「按会话」改成「按人」，`peer` 退回成「这条发生在哪个通道」这个属性。

### 三个新字段

| 字段 | 是什么 | 取值 |
|---|---|---|
| `owner` | 这条记忆**关于谁 / 谁说的**（QQ 号） | `'3022464706'` / `NULL`=归属未知 |
| `visibility` | 这话能在哪说 | `'dm_only'`（只在私聊提）/ `'public'` / `NULL`（未标注，**当 public**）|
| `is_self` | 这条是**我自己说的话**（出站） | `0` / `1` |

### 群聊记忆怎么拿到发言人的（原以为拿不到，其实一直有）

任务初稿里写的是「群聊记忆 owner 只能 NULL，因为 ingest 拿不到发言人 QQ」。
**实测不是这样，这个判断是错的。** `logs/bridge.out` 的入站行长这样：

```
2026-10-23T10:22:15.036Z 入站 group:1017567471 from=信风(3022464706) text="图片接收正常"
```

`RE_INBOUND` 正则（`memctl.py:83`）**一直就捕获了 `(?P<qq>\d+)`**，只是 v3 之前
没把它传进 `remember()`，只写进了 `memory/log/*.jsonl`。实测 452 条入站日志里
带 `from=昵称(QQ)` 的是 **452 条，覆盖率 100%**。

所以 v4 做的是：**ingest 时把 `m.group("qq")` 当 owner 传进去**，群聊记忆直接归到
发言人。这不是「估算」或「猜」，是日志里就有的字段。

### 老库迁移（684 条，已生产验证）

跟 `importance` 一样的模式：**只在 `owner` 列不存在时迁移一次**，之后
`connect()` 什么都不做。原因是回填要读 `logs/bridge.out` + `memory/log/*.jsonl`，
几百毫秒的活，而且会把手动标注过的 `visibility` 重算掉。

回填规则（`backfill_owner()`）：

1. 出站行（`bridge.out` 的 `出站 <peer> text="..."`）→ `is_self=1`、`owner=NULL`
2. `c2c-<qq>` → `owner=<qq>`（私聊只有一个人）
3. `group-<群号>` → 用 `(peer, 文本)` 在 `memory/log/*.jsonl` 里**精确对出**发言人 QQ；
   同一句话被多个发言人说过 → `owner=NULL`（不瞎猜）
4. 都对不上 → `owner=NULL`

**实测回填覆盖率**（生产库 684 条，迁移耗时 44ms，`integrity_check=ok`）：

| 类别 | 条数 | 归到 owner |
|---|---|---|
| `c2c` 非出站 | 294 | **294 / 294 = 100%** |
| `group` | 318 | **283 / 318 = 89.0%** |
| 出站（我说的） | 72 | 0（`is_self=1`，按设计不归给对端）|
| **合计** | 684 | **577 / 684 = 84.4%** |

没归上的 35 条**全是群聊里 owner=NULL 的条目**，其中大多数是
`reflect()` 产出的**群聊反思摘要**（如「他凌晨五点多还在线…」）——那是把整个群的
对话一起喂给模型提炼出来的，一句话里混了多个说话人，**归属本来就不唯一**，
硬塞给某个人是错的。另有 1 组是同一句话被 3 个发言人重复说过（`ambiguous`）。

**已知限制（如实记录）**：这 35 条群级记忆 `owner=NULL`，`recall_for_person(qq)`
不会返回它们。所以桥用的入口 `recall_with_visibility()` 默认会**额外带上本 peer
里 owner 未知的条目**（`include_peer_context=True`）——不这么做会丢群级知识，
A/B 实测里「头像」「B站」两个查询就退化成找不到了。

### 出站为什么 owner=NULL（而不是归给对端）

我自己的回复**不属于「关于这个人我知道什么」的画像**——它是「我当时怎么说的」，
那件事由风格库（`stylebank.py`）负责。混进来会污染对方的画像检索：
问「他是个什么样的人」，结果顶上来一堆我说过的话。

也不归给 agent 自己：`owner` 的语义是「这条记忆的主体是谁」，
如果把自己的话也标成 owner=自己，`recall_for_person()` 就得额外排除，
反而更容易写错。所以用**独立字段** `is_self=1` 表达，语义干净：
- 默认 `include_self=False`：对方的画像里没有我的话
- 要看「我对这个人说过什么」：`include_self=True`，靠 `c2c-<qq>` 反查
  （出站行的 peer 就是对端，所以能精确找回）
- 群里的出站无法归到具体说话人（我在群里发言不针对某个人）→ 不纳入

### visibility：不自动猜，默认全 public

**没有做任何自动 dm_only 判定。** 理由是瞎标的代价不对称：漏标只是「群里多说
一句」，错标会让它**该说的时候不敢说**，那更糟。所以迁移后 `visibility` 全是
`NULL`，语义上等于 `public`。

唯一的可靠来源是**手动标注**：

```bash
# 把 id 123 标成「只在私聊提过」
python3 memory/memctl.py set-visibility 123
# 一次标多条
python3 memory/memctl.py set-visibility 123 456 789
# 整条会话都标（慎用）
python3 memory/memctl.py set-visibility --peer c2c-3022464706
# 标回 public（撤回之前的 dm_only）
python3 memory/memctl.py set-visibility 123 --public
```

生产库里 684 条**目前没有一条被标 dm_only**——这是诚实的现状：能力有了，
但自动判定没做，得等手动标或以后由 LLM 辅助。所以现阶段「群聊不说私事」这个
约束**实际还没生效**（库里没有 dm_only 数据），它生效的前提是有人真的标了。

### 新检索接口

```bash
# 跨通道按人检索（c2c + 所有群一起找）
python3 memory/memctl.py recall-person --qq 3022464706 --query "撤回" --top 8

# 群聊场景：过滤掉只该在私聊说的
python3 memory/memctl.py recall-person --qq 3022464706 --query "考试" --in-group

# 看归集情况和覆盖率
python3 memory/memctl.py owners
```

Python 侧三个函数：

| 函数 | 用途 |
|---|---|
| `recall_for_person(conn, qq, query, top, in_group)` | 纯按人跨通道（不含本通道 owner=NULL 条目）|
| `recall_with_visibility(conn, peer, query, top, in_group, speaker)` | **给桥用的入口**：算不出 owner 就原样委托 `recall()`；算出就跨通道 + 带上本 peer 群级记忆 |
| `set_visibility(conn, ids, peer, dm_only)` | 手动标注可见性 |

**桥还没接。** 阶段一（本次）只做记忆层，`bridge/index.js` 一行没动。
桥现在的调用点 `bridge/index.js:1737`（`buildTopicHints` → `memctl recall --peer ...`）
**行为完全没变**，因为 `recall()` 一个字符都没改。要让跨通道生效，桥需要：
1. 群聊时把发言人 QQ 传进来（`speaker`）
2. 把 `recall` 换成 `recall_with_visibility`

## v3：检索从 bigram 字面重合升级为 BM25（带 IDF）


v2 的 `relevance()` 是：

```python
inter = len(query_tokens & mem_tokens)      # 命中几个词
return min(1.0, inter / math.sqrt(len(mem_tokens)))
```

短板**不是没语义，是没有 IDF**：`觉得`、`以后`、`现在`这种满库都是的高频词，
和 `delete_msg`、`底裤`这种只在一两处出现的专有词，**权重完全一样**（各算命中 1 个）。
于是「觉得 撤回」这种查询，会被一条满是「觉得」的废话压过真正讲撤回的那条。

v3 换成标准 BM25（纯 Python，约 60 行，不引依赖）：

```
score(q,D) = Σ IDF(t) · tf(t,D)·(k1+1) / (tf + k1·(1 − b + b·|D|/avgdl))
IDF(t)     = ln( (N − n(t) + 0.5) / (n(t) + 0.5) + 1 )
k1 = 1.5 , b = 0.75        （标准值，实测本库 b=0.75 已接近最优）
```

三个实现要点：

1. **倒排索引 + 进程内缓存**：语料指纹 = `(库文件, 未归档条数, MAX(id))`，
   变了才重建。冷建 13.8ms（671 条，4593 词表），热查询 2.39ms——
   比旧实现（4.43ms，每次重算分词）还**快近一倍**。
2. **查询内归一化**：BM25 原始分无上界，不能直接跟 importance/recency 加权，
   所以 `relevance = raw / 本次查询最高分` ∈ [0,1]。同一查询内排序不变，尺度稳定。
   （注意：归一化会让**含查询词的条目**散布在 (0,1]，但零重合仍严格为 0，
   所以「有 query 但零重合折损 25%」那条规则完全不受影响。）
3. **保留旧签名**：`relevance(row, query_tokens)` 不变，多了一个可选 `index=`
   参数（`recall()` 传进来免得每条重查缓存）。完全不传时退回旧公式兜底，不崩。

### A/B 实测结果（诚实记录）

**测试方法**：拿生产库的 `/tmp` 副本，12 个单 token 查询 + 8 个多 token 查询 +
8 个「噪音词混专有词」压力查询，逐条读全文人工标注相关性（2=直答 / 1=沾边 / 0=不相关），
算 nDCG@3 和 P@3。不是看谁排前面就夸谁。

| 测试集 | 旧 bigram | BM25(带IDF) | BM25(IDF恒等) | 结论 |
|---|---|---|---|---|
| 12 个单 token 查询 | nDCG **0.9289** | 0.9196 | — | **略降 −0.009** |
| 8 个多 token 查询 | 0.9320 | **0.9700** | 0.9700 | 提升 +0.038 |
| 8 个噪音+专有词混合 | 0.6478 | **0.8919** | 0.7606 | 提升 **+0.244** |

**必须说清楚的三件事**：

1. **单 token 查询上 BM25 没有改善，甚至略降 −0.009**。原因很实在：只有一个查询词时，
   IDF 是个全局常数，分子分母同比例缩放，**对排序零影响**。那一轮实际只测到了
   「BM25 长度归一 vs 旧的 sqrt 长度惩罚」，b=0.75 会系统性抬高短句，
   于是「性格」这类查询里短句「加点性格」更容易占顶——不过它恰好就是正确答案，所以只亏了一点。
   这个跌幅在 12 条样本上属于噪声量级，但**我不粉饰：单 token 没变好**。
2. **IDF 的价值在混合查询上非常明确**：关掉 IDF（恒等=1）后 nDCG 掉 0.1312
   （0.8919 → 0.7606）。典型例子：`老大 B站` 旧公式 top-3 全部 0 分相关，
   BM25 正确把「13 个 B站 MCP 工具挂进 QQ agent」顶到第 1。
3. **仍有 2 个查询变差**（`以后 开会`、`就是 情绪 模块`）：前者是「以后」这个词
   在库里只有 2 篇，IDF 反而很高，把「那我以后给你正个咋样」顶了上来。

一句话总结：**BM25 修的是「噪音词带偏检索」，这个修复是真实有效的（混合查询 +0.244）；
纯单关键词查询本来就没什么可修的，别指望它变好。**

### 已知副作用 / 取舍

- **b=0.75 会抬高短句**。本库 avgdl 只有 17.6 词（大量「嗯」「好」级别的短记忆），
  所以短句拿到的长度加成比较明显。网格搜过 b∈[0,0.9]，b=0.75 的 nDCG 0.8919
  已在最优平台区（b=0 是 0.8875），**没必要为这点差异偏离标准值**。
- **IDF 统计用全库、不按 peer 切**。理由是文档频率需要整个语料才准；
  候选条目仍然按 peer 过滤。所以同一条记忆在不同 peer 下的 relevance 绝对值一致。
- 桥（`bridge/index.js`）调的是 `recall` **不带 `--query`** 的路径（拿话题线索用），
  那条路径 relevance 恒为 0.5、根本不过 BM25——**这次改动不影响桥的现有行为**，
  只影响带 `--query` 的 CLI 检索和测试。
  （已验证：固定时间戳下，无 query 时新旧 `combine()` 分数**逐位完全相同、偏差 0.00e+00**。）

## 为什么改版（v1 → v2）

v1 能跑，但**检索很简陋**。实测发现的三个问题：

| 问题 | 表现 |
|---|---|
| **只有时间维度** | 「三小时前的一句废话」排序会排在「一个月前的重要约定」前面 |
| **没有重要性** | 222 条库里，大部分是 `唔，好毒，好像人`、`回个干啥就好了` 这种噪音 |
| **没有相关性** | 问「开会」时检索不到开会那条，只看谁新 |

还有个更根上的问题：**桥只记录入站消息，不记录我说了什么**。所以记忆里
只有「对方说过什么」，看不到「我答应过什么」——记不住自己的承诺。

## v2 的做法

### 检索公式（按 Stanford Generative Agents 论文）

`Generative Agents: Interactive Simulacra of Human Behavior`（arXiv:2304.03442）§4.1
里给了一个被广泛采用的检索公式：

```
score = α_relevance · relevance + α_importance · importance + α_recency · recency
```

三个分量都归一到 [0,1]。论文用等权，**但我们这边实测等权有坑**：

> query = 「情绪」时，一条 relevance=0.32 的「我给你加个情绪系统」
> 会输给一条 relevance=0、importance=0.8 的「明天下午三点开会」。
> 因为 importance 高 + recency 新，两项加起来压过了相关性 → **问 A 却答 B**。

所以权重改成 relevance 主导：

```python
ALPHA_RELEVANCE = 0.60   # 有 query 时，用户真正在问的东西
ALPHA_IMPORTANCE = 0.25
ALPHA_RECENCY = 0.15
```

还加了一条论文没有的规则：**有 query 但零重合 → 折到 25%**，
让「问情绪」不会被「开会安排」抢答。

### 三层记忆（认知科学标准分法）

| 层 | 存什么 | 半衰期 |
|---|---|---|
| `procedural` | 约定 / 规矩 / 怎么做事 | **365 天**（几乎不衰减）|
| `semantic` | 稳定事实：他是谁、喜欢什么、什么关系 | 60 天 |
| `episodic` | 具体对话片段 | 3 天 |

v1 只有一个「fact/person/topic」分类，且半衰期固定 14 天 —— 结果**约定会过期**，
三个月前的「只接你的活」会衰减到检索不出来。分层后不会了。

### importance 怎么算（不调 LLM）

论文让 LLM 打 1-10 分。我们**每轮都要打分，调 LLM 太贵**，所以用可解释的启发式：

```
基础分（由信息量决定，长度是最强信号）
  < 6 字  → 0.08    「嗯」「好」
  < 12 字 → 0.20
  < 25 字 → 0.35
  < 60 字 → 0.50
  < 150 字→ 0.58
  更长    → 0.50   （整段粘贴反而降）

加分项（独立累加）
  长期意味词（记住/以后/每次/规矩…）  +0.12/个，上限 0.30
  时间/日期（三点、10月26日）         +0.15
  地点（几楼、会议室…）               +0.10
  长数字（QQ号）                      +0.08
  观点/偏好（我觉得/我喜欢/我习惯）    +0.12
  第一人称（我/你）                   +0.05

类型下限
  procedural（规矩）→ 至少 0.70
  semantic（事实）  → 至少 0.45
```

**第一版失败过**：`长度×0.35 + 长期词×0.35 + 实体×0.30` 这种加权，
90% 的条目挤在 0.26、最高只到 0.42 —— importance 等于没有区分度。
改成「基础分 + 加分项」后，分布变成 0.08 → 0.75，这才有用。

### 出站也记，但降权

桥现在会记录我的回复内容（`出站 <peer> text="..." chars=N`）。
入站时：

- **对方说的话**：正常打分，可以 pin
- **我说的话**：强制 `episodic`、importance ×0.6、**绝不 pin**

因为记忆该以「对方告诉我的」为主，我自己的话只是让对话有上下文，
不该和对方立的规矩同权重。

### 强记忆点（pin）加了闸

v1 的 pin 判定太松，实测 10 条 pin 里一半是噪音：

```
✗ 那我以后给你正个咋样        ← 是讨论，不是规矩
✗ 已开启：proactive 已启动    ← 是我在汇报状态，不是他立的规矩
✗ 桥没给撤回能力，只能发不能撤  ← 是陈述，不是要求
```

v2 加三道闸：

1. **不能是疑问句/讨论语气**（咋样、行不行、吗、我觉得、可能…）
2. **不能是状态汇报**（已开启、已启动、已提交…）
3. **得真有规矩句式**，或者**带明确时空锚的承诺**（明天三点开会）

同时修了一个隐藏 bug：pin 的 importance 原先一律设 0.95 →
所有 pin 并列，importance 又失去区分度。现在抬到 0.8 下限，保留差异。

## 定期反思（reflection）—— 真正调模型的提炼

论文 §4.2 的 Reflection：定期回头看最近的记忆，提炼成更高层的「反思」。
之前 `consolidate()` 只是把同关键词的几条拼成一句，**不是提炼**。现在实现了真的：

```bash
# 对最近 24h 的 episodic 跑一次反思（会真的调一次模型）
python3 memory/memctl.py reflect --peer c2c-3022464706 --hours 24

# 所有 peer 都跑
python3 memory/memctl.py reflect

# 只看提炼结果，不写库
python3 memory/memctl.py reflect --dry-run

# 没有模型的环境：退回老的拼接法
python3 memory/memctl.py reflect --no-llm

# 分批参数（默认就是这几个值，一般不用改）
python3 memory/memctl.py reflect --batch 10 --timeout 90 --total-timeout 600
```

### 分批提炼（为什么必须分批）

曾实测过：把 59 条 episodic **一次性**拼进一个 prompt → 单次调用 180 秒超时失败
（返回 `mode='error'`、`created=0`）；而 3 条的小 prompt 只要 42 秒就成功。
所以瓶颈是**单次输入太大**，不是模型不可用。

现在 `reflect()` 按 `batch=10` 切批，逐批调用：

- 每批单独一个 prompt（10 条 ≈ 几分钟内稳定返回），结果合并后按指纹去重
- **单批失败不连累全局**：该批的 episodic 保持 `reflected=0`（下轮还能重试），
  继续跑后面的批，返回里带 `batches_failed` 计数
- **只有全部批都失败**才 `mode='error'`，此时一条数据都不改
- 部分成功/超预算 → `mode='llm-partial'`，已成功的批次照常入库并打标记
- **总超时预算** `total_timeout=600` 秒：累计超了就不再起新批，
  已成功的存下来（不白跑）
- 单批超时默认 `timeout=90`（小批够用，且失败更快暴露）

### 它让模型提炼哪几类

只记这五类，其他一律不要：

1. 这个人的身份/基本情况（称呼、所在、职业、作息）
2. 明确的偏好与雷点（喜欢什么、讨厌什么、别对他做什么）
3. 你们之间的约定和规矩
4. 没做完 / 待办的事
5. 关系变化（称呼变了、态度变了）

并且硬性要求：每条一句话 20~60 字、**必须脱离上下文独立看懂**、
只用对话里真出现过的信息、不许推测。

### 实测效果（真实模型，非 mock）

私聊 49 条 episodic → 提炼 5 条：

```
+ 对方是信风（QQ 3022464706），说过我是他教出来的，除了原谅我还能干嘛。
+ 信风偏好我回复只写一行就够了，不要后续解释补充，越像人越好。
+ 规矩：只接信风(3022464706)的干活请求，其他人一概不接活儿。
+ 每 20 分钟的搭话判断要从我最后一次发言开始计时，目前只在和信风的私聊生效、群里不生效。
+ 待办：桥目前只能发不能撤，撤回要另加 delete_msg；信风还答应一会儿更新我的人格。
```

群聊 65 条（噪音更多）→ 也提炼出 5 条，其中一条是**未完成的事**：
```
+ 对方让查看 BV14Ln46zE4y 的评论区，之后没再提结果。
```
这种「说了没下文」的信息，拼接法永远提炼不出来。

### 幂等与失败安全

- 被提炼过的 episodic 打 `reflected=1`，**下次不重复提炼**（实测第二次扫描 0 条）
- 分批后：**只给成功处理的批打标记**，失败/没跑到的批保持 `reflected=0` → 下轮自动重试
- 所有批都失败 → `mode='error'` 且**不改任何已有数据**、不打标记 → 上层可重试
- 部分批失败 → `mode='llm-partial'` + `batches_failed`，成功那部分照常入库
- LLM **不可用**（没配模型/起不来）→ 静默退回拼接法，不报错
- 模型回「无」→ 正常结果（0 条），但照样打标记，避免反复扫同一批废话

### 实现方式

- 核心函数 `reflect()` / `reflect_all()` / `_parse_reflection()` 在 `memctl.py`
- 调模型走薄壳 `reflection_llm.mjs`（复用 `bridge/acp.js` 的 `AcpRuntime`，
  读 `bridge/config.json` 的主路由，不另配一套模型）。
  它**不挂 MCP**（反思只需读记忆，省启动时间和 token）
- Python 与 Node 通过临时文件交换 prompt/结果，Python 侧完全不碰 ACP 协议

## 已知的不足（诚实记录）

0. **按人归集的 35 条群级记忆 owner=NULL**（占群聊 318 条的 11%）。它们是
   `reflect()` 产出的群聊反思摘要，一句话混了多个说话人，归属不唯一。
   `recall_for_person(qq)` 取不到它们；桥用的 `recall_with_visibility()` 默认
   额外带上，但纯按人检索会漏。**这是真实限制，不是已经解决了。**

0b. **`visibility` 自动判定没做**，684 条全是 NULL（= public），只有手动命令能标。
   所以在有人标之前，「群里不说私聊的事」这条约束**实际没生效**。
   不想为了填字段瞎猜——错标 dm_only 会让它该说话时不敢说，比漏标更糟。

1. **分类还不准**。`procedural` / `semantic` / `episodic` 是靠关键词猜的，
   会把「我给你加个情绪咋样」归到程序记忆。不影响检索（有 relevance 兜着），
   但影响 digest 的分组可读性。

2. ~~consolidate 很粗糙，不是真正的提炼~~ **已解决：实现了真正的 reflection**（见下节）。
   `consolidate` 仍保留作为「无模型环境」的降级路径。

3. **importance 是启发式**，不是语义理解。反讽（「你可真行啊」）会被当成夸。
   要更准就得让 LLM 打分，代价是每轮多一次调用。

4. **没有时间推理**。「上周说的那件事」这种相对时间表述，检索不出来。
   需要把时间也索引化（目前只按时间戳衰减，不做语义时间解析）。

5. **BM25 索引缓存不跟踪「原地改 text」**。缓存指纹是
   `(库文件, 未归档条数, MAX(id))`，所以只有新增/归档会触发重建。
   如果将来有人用 `UPDATE entries SET text=...` 原地改文本，索引会留旧词
   （**实测确认**：改完后新词检索不到，返回空）。
   目前生产代码里**没有**这种路径（`remember` 只改 hits/strength/importance/pinned/kind，
   不改 text），所以不是现实风险；真要改文本时记得调 `invalidate_bm25()`。

6. **BM25 不能解决「同词不同义」**。「情绪」查询会把「Chovy 补刀毫无情绪」
   和「给我加个情绪模块」混在一起排，因为字面上都是「情绪」。
   要分辨得靠 embedding 或 LLM 重排，不在本次范围。
